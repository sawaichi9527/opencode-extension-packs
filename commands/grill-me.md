針對下列主題進行需求訪談：

$ARGUMENTS

若沒有提供參數，使用目前對話中正在討論的計畫、功能或設計作為主題。

請遵守以下流程：

1. 先確認本 Session 是否已讀取 `AGENTS.md`、`handoff.md` 與 Git 狀態；檔案未變更時沿用既有結果，只補讀與本次主題直接相關的文件和程式碼。
2. 若 `AGENTS.md`、`handoff.md` 或 Git Repository 不存在，略過該項，不視為錯誤。能由 Repository 或工具查明的事實不要反問使用者。
3. 只詢問需要由使用者決定的事項，而且每次只問一題，等待回答後再繼續。
4. 每一題都附上你的建議答案與簡短理由，但最終決定由使用者確認。
5. 使用者擁有範圍決定權：可以反駁或改寫你的題目，也可以回答「不知道」。訪談結束的判準是「已沒有未處理、未被默默假設的分支」，不是問滿固定題數。
6. 遇到無法只靠討論回答、需要先有可反應的東西才能決定的問題（例如手感、外觀或取捨體驗），停止追問，明確標示「這題需要先驗證」，建議先離開本訪談做最小原型或實驗，取得結果後再回來接續；不要在同一個無解問題上反覆改問法。
7. 優先釐清：目的、範圍、不包含範圍、限制、成功條件、失敗條件、驗證證據、錯誤處理、介面、資料流、DUT／硬體影響與安全邊界。
8. 遇到「正常、完成、成功、失敗、Log、封包、Timeout、支援」等可能有多種解釋的詞，必須轉成可觀察、可測量或可驗證的定義。
9. 對 Python、UART／TTY、Console Log 或 Wireshark／PCAP 工作，確認原始證據、Parser 結果、時間基準、Verdict 與 Artifact 保存方式。
10. 不要為了訪談新增 `CONTEXT.md`、ADR、plan 檔或其他規格框架。只有使用者明確要求保存結果時，才使用專案既有的文件結構。
11. 在雙方確認已達成共同理解前，不建立程式碼、不修改檔案，也不開始實作。

訪談完成時，整理：

- 目的
- 範圍
- 不包含範圍
- 已確認的重要術語
- Acceptance Criteria
- 必須保留的驗證證據
- 重大決定與理由
- 尚未確定事項
- 建議的下一步

顯示摘要後等待使用者確認，不要自行進入實作。
